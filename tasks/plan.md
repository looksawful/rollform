# ROLLFORM · План UX и дизайн-системы для прототипа
Дата: 2026-11-08 · Статус: **предлагается к реализации после просмотра** · Трекер: looksawful/rollform-internal #5 и текущая задача Asana.

Связанные документы: [исследование шести дизайн-систем](../docs/research/rollform-design-system-benchmark-2026-11-08.md) · [AGENTS](../AGENTS.md) · [README](../README.md).

## 0. Цель и ограничения

Цель: довести **функциональность и качество интерфейса прототипа** до согласованного состояния без выдумывания сведений о реальных товарах. Посетитель может найти демовариант, изменить три параметра 3D-кубика, добавить его в корзину, разобраться в результате и проверить демонстрационную форму. Интерфейс работает на мобильном, с клавиатурой и при отключённых анимациях.

**Неприкосновенно:** существующие демоназвания, иллюстративные фото, Hero и утверждённые тексты; визуальная айдентика (Inter, светлая версия, чёрно-белые поверхности, округлые кнопки); реальные параметры GLB/материалов; текущие маршруты, корзина и URL-конфигурации. Не включать оплату/отправку сообщений, не утверждать наличие, доставку и характеристики без данных, не добавлять реальных оценок или отзывов.

**Отложено до реального каталога:** настоящие SKU и названия, сопоставление фотографий с конкретными товарами, реальные цены/остатки, гарантии, стоимость доставки, коммерческий checkout и финальные тексты. Не считать фото и демоназвания дефектами в рамках этой инициативы.

**Проверенное состояние на момент составления:** 9 демопозиций, 2 колонки каталога на 390 px, кнопка каталога на мобильном с CSS font-size 0.75rem (12 px), выбор D4/D6/D8/D10/D12/D20/D% + цвет + шрифт, live 3D-превью, работающая демокорзина (пустое состояние, количество, удаление, очистка), формы контакта с подтверждением «не отправлено» и fallback 3D. В проекте уже есть semantic tokens и Stack/Cluster/Grid/Reel. Полный браузерный тест существует в tests/navigation.browser.mjs.

## 1. Зафиксированные решения и проектная модель (Plan + GrillMe + Ponytail)

1. **Источник выбранного кубика** — тип `DiceConfig` и существующий `src/lib/catalog.ts`. Не вводить второй независимый store, Redux, каталог материалов или API для демопрототипа.
2. **Один главный CTA на экран**. Каталог может иметь вторичное «в корзину»; страница товара и конструктор предлагают действие покупки без ложной обработки платежа.
3. **Липкое действие в конструкторе, не две панели.** На узком экране повторно использовать существующие цену и CTA в одном sticky-контейнере, если чистый CSS проходит проверку; иначе компактная единственная сводка без второй WebGL-сцены.
4. **Фото и 3D-различаются по назначению.** Не пытаться доказать соответствие демофотографий демоконфигурациям. Любые будущие товарные фотографии должны иметь отдельный контракт с реальным SKU. Текущие фото не переименовывать и не заменять.
5. **Светлая тема сейчас одна**; dormant dark tokens не удалять, кнопку переключения не показывать.
6. **Встроенные средства прежде пакетов:** CSS для оформления/стикера, `aria-pressed`/`role=status` и native validation, существующие GSAP/Three/Lucide. Никаких Material/Carbon/Gravity/Tailwind зависимостей.
7. **Документируем существующее, а не изобретаем новое:** DESIGN.md по реальным tokens.css и компонентам; Storybook только как витрина реально используемых состояний, если проекту действительно нужна интерактивная внешняя приёмка. Не дублировать старые Storybook-проекты или выдавать демо за production.

## 3. Задачи в порядке исполнения

### RF-01 · Реестр и контракт состояний компонентов (P0, S)
**Зачем:** сейчас состояния повторяющихся паттернов не зафиксированы как единый контракт.
**Изменить:** только спецификацию. Инвентарь по настоящим CSS/TSX: Button (primary/secondary/text/icon), ChoicePill, ProductCard, Price, CartLine, Gallery, DiceViewer, FormField и Menu.
**Матрица:** для каждого применимого элемента — default, hover (только hover-capable), focus-visible, active/pressed/selected, disabled, loading/error/success/empty (только где возможны). Указать источник истинного состояния и факт отсутствия state.
**Приёмка:** каждый реальный компонент/паттерн имеет владельца, допустимые состояния и скрин/тест; не предлагаются фиктивные состояния вроде loading для статического текста.
**Файлы:** будущий `DESIGN.md`, существующие `src/styles/tokens.css`/`components.css` для чтения.
**Проверка:** ручная сверка всех восьми маршрутов, 320/390/768/1440, клавиатура и CSS media queries.
**Зависимости:** нет. **Трекер:** #2, #5.

### RF-02 · Нормализовать существующие токены и композицию (P1, S–M)
**Зачем:** пока размеры и отступы корректировать локально легко, но важно не допустить новых исключений.
**Изменить:** сохранить существующие `--fs-*`, `--space-*`, `--radius-*`, `--color-*`. Определить повторяемые роли — обычная кнопка, компактная кнопка карточки, заголовок+лид, поле ввода, интерактивный фокус. Добавлять токен только если ≥2 компонента нуждаются в одном новом значении; убрать только доказанные дубли.
**Приёмка:** нет произвольных внутренних размеров у повторяющихся элементов; типографические группы и фокус консистентны на всех основных маршрутах; Hero/copy не изменены.
**Файлы:** `src/styles/tokens.css`, `src/styles/pages.css`/`components.css`, `tests/typography.test.mjs`.
**Проверка:** тесты типографики, визуальное сравнение мобильной и десктопной версии, отсутствие horizontal overflow.
**Зависимость:** RF-01. **Трекер:** #2.

### RF-03 · Мобильные карточки каталога: читаемость и размеры (P0, S–M)
**Зачем:** на узком экране подпись действия 12 px и двустрочные кнопки создают шум.
**Изменить:** сохранить 2 колонки, фото, цену и одинаковую высоту карточек. Добиться текста действия ≥14 px и зоны нажатия ≥44×44 CSS px, разрешить логичное перенесение/компоновку значка и подписи без обрезки. Основную ссылку на товар не накрывать кнопкой корзины.
**Приёмка:** на 320/390/430 px нет обрезки, наложений, мелких интерактивных областей; на 768/1440 карточки сохраняют ритм; добавление/открытие различимы.
**Файлы:** `src/components/ProductCard.tsx` (если понадобится), `src/styles/pages.css`, `tests/navigation.browser.mjs`.
**Проверка:** браузерный bounding-rect/focus тест и скрины на 320,390,430,768,1440.
**Зависимости:** RF-01–02. **Трекер:** #2.

### RF-04 · Краткие характеристики демовариантов (P1, S)
**Зачем:** форма и цвет есть в `presets.config`, но не видны в списке; названия остаются заглушками.
**Изменить:** под временным названием компактно отображать форму и цвет **из уже существующего config**. Не добавлять придуманные атрибуты, новые фильтры, теги «хит», реальные фотографии или товарные описания. В карточке товара расширенные параметры уже есть.
**Приёмка:** видимые форма и цвет каждого из 9 вариантов совпадают с демоданными и корзиной; новая строка не ломает CTA; обновление config в одном месте отражается всюду.
**Файлы:** `ProductCard.tsx`, `src/styles/pages.css`, тест `tests/storefront-redesign.test.mjs`.
**Проверка:** кодовые и браузерные проверки параметров 9 вариантов.
**Зависимость:** RF-03. **Трекер:** #5.

### RF-05 · Единая обратная связь «добавлено» (P1, S–M)
**Зачем:** действие уже меняет количество, но стандарт обратной связи различается в каталоге, детали, конфигураторе.
**Изменить:** использовать существующее состояние `useCart`, бейдж корзины, кнопку и локальный `role=status`. Уточнить доступное announce без навязчивых всплывающих тостов. Не показывать ложное «оформлено» и не создавать второй глобальный toaster.
**Приёмка:** одна попытка добавления = одно увеличение count и одно корректное озвучивание; при отказе/лимите 99 показывается понятный результат; сохраняется после перезагрузки; keyboard/VoiceOver/NVDA не дублируют сообщения.
**Файлы:** `ProductCard.tsx`, `CartState.tsx`/`ProductDetail.tsx` при необходимости; `tests/product-flow.test.mjs`, `tests/navigation.browser.mjs`.
**Проверка:** add из каталога/товара/конструктора, reload, limit 99, screen reader.
**Зависимость:** RF-01. **Трекер:** #10, #16.

### RF-06 · Мобильная сводка выбора, цены и CTA в конструкторе (P0, M)
**Зачем:** при прокрутке выбора шрифта 3D-предпросмотр и цена уходят вверх/вниз.
**Изменить:** сохранить 3 группы `shape → shell → font` и URL-состояние. На <=56rem протестировать **одну** sticky-панель с кратким текущим выбором, ценой и действием; использовать существующую цену и кнопку, а не создавать их дубль и новый WebGL canvas. При видимом исходном buy-блоке панель не повторяется. На больших экранах использовать текущую верстку.
**Приёмка:** форма/цвет/шрифт меняют цену/параметры синхронно, URL/share/reload работают; CTA не накрывает варианты/клавиатуру iOS и не конфликтует с bottom safe area; 320/390/430/768/1440 без layout shift/overflow; при открытии экранного меню и масштабировании 200% доступен последний вариант.
**Файлы:** `Configurator.tsx`, `pages.css`/`responsive.css`, `tests/navigation.browser.mjs`.
**Проверка:** touch scroll, orientation, browser zoom, iOS Safari, keyboard, config URL restore.
**Зависимости:** RF-01–02, RF-05. **Трекер:** #5.

### RF-07 · 3D-превью: загрузка, недоступность, повторная попытка (P1, M)
**Зачем:** модель может долго грузиться/не запуститься при WebGL context loss или слабом устройстве.
**Изменить:** переиспользовать уже существующий `fallback` в `DiceViewer` и обработку context lost/restored. Продумать последовательность idle/loading/ready/error, статическую подложку текущей формы/цвета, честное озвучивание состояния без ложной доступности 3D. Retry только если реально нужен; не создавать глобальный loading store.
**Приёмка:** контент и CTA не исчезают при отключённом WebGL; нет бесконечного спиннера; при восстановлении контекста нет дублирования canvas и утечки; при загрузке preview не прыгает; Hero остаётся пассивным, другие модели сохраняют управление.
**Файлы:** `DiceViewer.tsx`, стили canvas/preview, `tests/dice-motion.test.mjs` и браузерный тест.
**Проверка:** WebGL disabled, slow network, context lost/restored, reduced motion, Chrome + мобильный Safari.
**Зависимость:** RF-01, RF-06. **Трекер:** #5.

### RF-08 · Демосценарий «товар → корзина → контакты» (P1, M)
**Зачем:** настоящего checkout нет, а слова «Купить», «Оформить заказ», «В наличии» могут вводить в заблуждение.
**Изменить:** не менять утверждённые копирайт-тексты без решения пользователя. Зафиксировать **поведенческую** семантику: «Добавить» изменяет только локальную корзину, «Купить» ведёт в неё, «Оформить» открывает демонстрационную форму, не списывает деньги и не отправляет заявку. Существующую подсказку о демо показать в точке контакта с действием, только если это можно сделать без переписывания авторского текста.
**Приёмка:** ни один экран не подтверждает оплату/размещение реального заказа; возврат не теряет корзину; сумма и количество совпадают на всех экранах; нет фиктивных шагов оплаты.
**Файлы:** `ProductDetail.tsx`, `CartView.tsx`, `ContactContent.tsx` только при необходимости; `tests/product-flow.test.mjs`.
**Проверка:** полный путь без выполнения внешних действий.
**Зависимости:** RF-05. **Трекер:** #10, #13.

### RF-09 · Корзина: пределы и разрушительные действия (P1, S–M)
**Зачем:** корзина уже умеет всё нужное; осталось закрепить границы.
**Изменить:** проверить item limit и расхождение между старым `items` и queued updater в `CartState.add`, что ранее зафиксировано в #16. Не добавлять modal на каждое удаление. Рассматривать undo при «Очистить корзину» лишь если тест покажет частые ошибочные нажатия; для прототипа достаточно безопасной визуальной и клавиатурной реакции.
**Приёмка:** add 1–99, remove, clear и reload детерминированы, не сообщают «успех», если add не состоялся; пустое состояние сохраняет путь назад в каталог.
**Файлы:** `CartState.tsx`, `src/lib/orders.ts`, `CartView.tsx`, `tests/product-flow.test.mjs`.
**Проверка:** быстрые двойные нажатия, 99→99, несколько разных preset/custom, reload/storage denied.
**Зависимости:** RF-05. **Трекер:** #10, #16.

### RF-10 · Контактная форма: понятные validation/error/demo-success (P1, S–M)
**Зачем:** поля уже имеют label/required, демо подтверждает, что сообщение не отправлено; уточнить плохие состояния.
**Изменить:** проверить браузерную native validation и focus первого недопустимого поля, email keyboard/autoComplete, читаемость и текст под ошибкой, сообщить о «не отправлено» после успешной локальной валидации. Не подключать сервер, почту, CAPTCHA, регистрацию.
**Приёмка:** валидные/невалидные значения, пустые поля, длинные имена, отсутствие сети, возврат с корзины; сообщение не отправляется и данные не сохраняются; ошибка не сбрасывает введённое; SR получает результат.
**Файлы:** `ContactContent.tsx`, `pages.css`, `tests/navigation.browser.mjs`.
**Проверка:** touch keyboard iOS, tab/Enter, axe/ручной SR, тесты без внешних запросов.
**Зависимости:** RF-01 и RF-08. **Трекер:** #13.

### RF-11 · Аудит доступности полного пути (P1, M)
**Зачем:** повторяющиеся компоненты требуют одинаковых правил, не отдельной бесконечной «доступности всего».
**Изменить:** проверить семантические headings, contrast WCAG AA (обычный текст 4.5:1, крупный 3:1), focus-visible, touch target минимум 44×44, подписанные icon buttons, правильные `aria-pressed`, radio-like группы, отсутствие ловушек фокуса в lightbox; клавиатура, reduced motion. Исправлять в исходных компонентах; новый a11y runtime пакет не нужен.
**Приёмка:** любой путь (каталог → детали → конструктор → корзина → контакты) проходим клавиатурой, не скрывает focus и не запускает принудительное движение; длинные подписи и 200% zoom не обрезаются.
**Файлы:** затронутые конкретным нарушением UI файлы, `tests/navigation.browser.mjs`.
**Проверка:** manual keyboard, NVDA/VoiceOver, axe по возможности, 320/390/768/1440, reduced motion. Измерять, не объявлять WCAG «пройденным» только по lint.
**Зависимости:** RF-03–10. **Трекер:** #5.

### RF-12 · Контроль motion, 3D-производительности и fallback (P2, M)
**Зачем:** мобильные рывки уже исправлены в `d40b360`, не чинить их повторно вслепую.
**Изменить:** baseline FPS / dropped frames, WebGL context count, LCP/CLS/INP, GLB и текстуры, CPU/GPU нагрузка при 3D + карусели на мобильном. Вывести общие duration/easing в токены лишь если доказана повторяемость. Учитывать visible/offscreen, reduced motion, touch pause. Переносить в 3D только измеренные оптимизации.
**Приёмка:** нет regressions motion/render; canvas отключается/останавливается вне viewport; карусель сохраняет hover/drag/keyboard и reduced-motion; показатели до/после записаны, а не придуманы.
**Файлы:** `DiceViewer.tsx`, `ProductGallery.tsx`, `src/styles/pages.css`/`tokens.css` только после профилирования, browser tests.
**Проверка:** Chrome DevTools performance, бюджет по реальному baseline и целевым устройствам, Safari iOS, Linux headed CI.
**Зависимости:** RF-06–07, RF-11. **Трекер:** #4, #15.

### RF-13 · Дизайн-система и витрина компонентов (P2, M, частями)
**Зачем:** обеспечить передачу знаний между исполнителями, а не плодить UI-фреймворк.
**Изменить:** (а) сгенерировать и проверить `DESIGN.md` из реальных `tokens.css` + паттернов `.wrapper/.stack/.cluster/.grid/.reel` + реальных стилей кнопок/полей; нормативен CSS, не второй набор CSS-токенов. (б) добавить матрицу компонентов, вариантов, состояний, размеров, применяемых в экранах; (в) Storybook как **отдельная согласуемая фаза** только для реально повторяемых компонентов/потоков, если он не установлен; проверить стоимость поддержки. Не создавать дизайн-систему с сотней атомов без потребителей.
**Приёмка:** одна актуальная карта компонентов; пример каждого реально используемого состояния, responsive и a11y; ссылка на source и маршруты, нет расхождения с CSS. Если Storybook будет выбран — stories тестируют production components и можно запустить локально; не создавать дублирующую верстку.
**Файлы:** `DESIGN.md` и/или существующая документация (после проверки правил), Storybook config/stories только в отдельном пакете. Текущий файл плана — источник последовательности, не отдельный журнал.
**Проверка:** инспекция по исходникам и скринам, component state coverage; после установки Storybook — билд витрины.
**Зависимости:** RF-01–02 и RF-11. **Трекер:** #5.

## 6. Допущения, спорные решения и стоп-лист (GrillMe)

- **A1: для прототипа нужна реальная интерактивность, но не реальная коммерция.** Если клиент захочет полноценную обработку заказов, потребуется новый продуктовый контракт/спецификация; текущую демонстрационную форму не превращать в отправку без запроса.
- **A2: фото, названия, сроки и цена не финальные.** Применять данные по существующим ключам; не заниматься выбором финального контента, не скрывать демо-статус там, где он помогает избежать ложного обещания.
- **A3: sticky buy bar уместен только если не крадёт вертикальное пространство.** При 320px, 200% zoom и экранной клавиатуре проверка обязательна, иначе альтернатива — обычный buy box после списка.
- **A4: Storybook нужен для переноса дизайн-решений между агентами, но тяжёл для малой библиотеки.** Начать с DESIGN.md и контрактов; отдельный gate на установку/интеграцию Storybook, не ставить «потому что большие компании так делают».
- **A5: 3D много на мобильном.** Не запускать WebGL на каждой карточке и в sticky buy bar, оставить существующий основной рендер и запасной статический вид.
- **A6: «унифицировать кнопки» не означает заменить все действия на одинаковые.** Различные функции остаются различимыми: открыть товар, настроить вариант, добавить в корзину, перейти к демоформе.
- **A7: навигация и цветовая тема утверждены.** Никакого навязанного bottom-nav и переключателя тёмной темы в рамках этого плана.
